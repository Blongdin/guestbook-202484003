# Spec: 미니 방명록 (guestbook-202484003)

Status: ready-for-agent

- 개발자: 김동현 (학번 202484003)
- 작성일: 2026-09-30
- 용어는 루트의 `GLOSSARY.md`를 따른다: **방명록 글**, **작성자**, **메시지**, **비밀번호**, **작성 시각**.

## Problem Statement

방문자가 회원가입이나 로그인 없이 짧은 메시지를 남기고, 다른 사람이 남긴 글을 볼 수 있는 공간이 필요하다. 계정이 없기 때문에 "이 글을 쓴 사람"만 자기 글을 고치거나 지울 수 있어야 하는데, 그 사람을 확인할 수단이 없다. 또한 이 과제는 실기시험이므로 Create / Read / Update / Delete가 로컬뿐 아니라 Vercel Production 사이트에서도 실제로 동작해야 하고, 비밀번호가 틀렸을 때 수정·삭제가 확실히 거부되어야 한다.

## Solution

단일 페이지 방명록을 만든다. 누구나 이름·메시지·비밀번호를 입력해 **방명록 글**을 남길 수 있고, 페이지에는 모든 방명록 글이 **작성 시각** 최신순으로 표시된다. 각 방명록 글에는 [수정] [삭제] 버튼이 있고, 누르면 그 글 아래에 입력 폼이 펼쳐진다. 글을 쓸 때 정한 **비밀번호**를 입력해야만 **메시지**를 수정하거나 글을 삭제할 수 있으며, 비밀번호가 틀리면 요청이 거부되고 폼 안에 "비밀번호가 일치하지 않습니다."라는 안내가 표시된다. 페이지에는 개발자 이름 김동현과 학번 202484003이 항상 보인다.

## User Stories

### 작성 (Create)

1. 방문자로서, 로그인 없이 바로 방명록 글을 남기고 싶다. 그래야 가입 절차 없이 가볍게 인사를 남길 수 있다.
2. 방문자로서, 이름·메시지·비밀번호 세 가지를 입력하는 폼을 페이지 상단에서 보고 싶다. 그래야 무엇을 입력해야 하는지 바로 안다.
3. 작성자로서, 비밀번호 입력란의 글자가 가려지길 원한다. 그래야 옆 사람이 내 비밀번호를 볼 수 없다.
4. 작성자로서, 글을 등록하면 새로고침 없이 목록 맨 위에 내 글이 나타나길 원한다. 그래야 등록이 성공했음을 바로 확인할 수 있다.
5. 작성자로서, 등록에 성공하면 작성 폼이 비워지길 원한다. 그래야 실수로 같은 글을 두 번 올리지 않는다.
6. 작성자로서, 이름·메시지·비밀번호 중 하나라도 비어 있으면 등록이 거부되고 무엇이 문제인지 안내받고 싶다. 그래야 입력을 고칠 수 있다.
7. 작성자로서, 공백만 입력한 값은 빈 값으로 취급되길 원한다. 그래야 내용 없는 글이 올라가지 않는다.
8. 작성자로서, 이름은 20자, 메시지는 500자, 비밀번호는 4–20자라는 제한을 넘으면 안내받고 싶다. 그래야 왜 등록되지 않는지 안다.
9. 작성자로서, 등록 요청 중에는 버튼이 비활성화되길 원한다. 그래야 중복 등록을 막을 수 있다.
10. 작성자로서, 다른 사람과 같은 이름으로도 글을 쓸 수 있길 원한다. 회원 개념이 없으므로 이름은 고유할 필요가 없다.
11. 작성자로서, 서버 오류로 등록에 실패하면 실패했다는 안내를 받고 입력한 내용은 유지되길 원한다. 그래야 다시 시도할 수 있다.

### 조회 (Read)

12. 방문자로서, 페이지에 들어가자마자 전체 방명록 글 목록을 보고 싶다. 그래야 다른 사람들이 남긴 글을 읽을 수 있다.
13. 방문자로서, 목록이 작성 시각 최신순으로 정렬되길 원한다. 그래야 가장 최근 글을 먼저 본다.
14. 방문자로서, 각 방명록 글에서 작성자 이름, 메시지, 작성 시각을 함께 보고 싶다. 그래야 누가 언제 무엇을 남겼는지 안다.
15. 방문자로서, 작성 시각이 한국 시간(`YYYY-MM-DD HH:mm`)으로 표시되길 원한다. 그래야 서버 위치와 무관하게 정확한 시각을 안다.
16. 방문자로서, 수정된 방명록 글에는 "(수정됨)" 표시가 보이길 원한다. 그래야 원래 내용이 바뀌었음을 안다.
17. 방문자로서, 메시지에 입력된 줄바꿈이 그대로 보이길 원한다. 그래야 여러 줄 메시지가 읽기 쉽다.
18. 방문자로서, 방명록 글이 하나도 없을 때 "아직 방명록 글이 없습니다." 같은 안내를 보고 싶다. 그래야 페이지가 고장 난 것이 아님을 안다.
19. 방문자로서, 페이지네이션 없이 전체 목록을 한 번에 보고 싶다.
20. 방문자로서, 메시지에 HTML이나 스크립트가 들어 있어도 글자 그대로 보이길 원한다. 그래야 악성 입력으로 페이지가 망가지지 않는다.
21. 방문자로서, 다른 사람의 비밀번호나 그 해시가 화면이나 네트워크 응답 어디에도 노출되지 않길 원한다.

### 수정 (Update)

22. 작성자로서, 내 방명록 글의 [수정] 버튼을 누르면 그 글 아래에 수정 폼이 펼쳐지길 원한다. 그래야 어떤 글을 고치는지 헷갈리지 않는다.
23. 작성자로서, 수정 폼에 기존 메시지가 미리 채워져 있길 원한다. 그래야 일부만 고칠 수 있다.
24. 작성자로서, 수정 폼에서 새 메시지와 비밀번호를 입력해 저장하고 싶다.
25. 작성자로서, 비밀번호가 맞으면 메시지가 바로 바뀌고 수정 폼이 닫히길 원한다.
26. 작성자로서, 비밀번호가 틀리면 수정이 거부되고 폼 안에 "비밀번호가 일치하지 않습니다."라는 안내를 보고 싶다. 그래야 무엇이 잘못됐는지 분명히 안다.
27. 작성자로서, 비밀번호가 틀렸을 때 내가 입력한 새 메시지가 지워지지 않길 원한다. 그래야 비밀번호만 다시 입력하면 된다.
28. 작성자로서, 이름은 수정할 수 없고 메시지만 수정되길 기대한다.
29. 작성자로서, 수정해도 내 글의 목록 위치(작성 시각 기준 정렬)가 바뀌지 않길 원한다.
30. 작성자로서, 새 메시지가 비어 있거나 500자를 넘으면 수정이 거부되고 안내받고 싶다.
31. 작성자로서, 수정 폼의 [취소]를 눌러 아무것도 바꾸지 않고 폼을 닫고 싶다.
32. 방문자로서, 그사이 다른 사람이 삭제한 방명록 글을 수정하려 하면 "이미 삭제된 방명록 글입니다." 안내를 받고 목록이 갱신되길 원한다.

### 삭제 (Delete)

33. 작성자로서, 내 방명록 글의 [삭제] 버튼을 누르면 그 글 아래에 비밀번호 입력 폼이 펼쳐지길 원한다.
34. 작성자로서, 비밀번호가 맞으면 방명록 글이 목록에서 즉시 사라지길 원한다.
35. 작성자로서, 비밀번호가 틀리면 삭제가 거부되고 폼 안에 "비밀번호가 일치하지 않습니다."라는 안내를 보고 싶다.
36. 작성자로서, 비밀번호 입력 자체가 확인 절차 역할을 하므로 별도의 확인 팝업 없이 삭제되길 원한다.
37. 작성자로서, 삭제 폼의 [취소]를 눌러 아무것도 지우지 않고 폼을 닫고 싶다.
38. 방문자로서, 이미 삭제된 방명록 글을 삭제하려 하면 "이미 삭제된 방명록 글입니다." 안내를 받고 목록이 갱신되길 원한다.
39. 방문자로서, 한 번에 하나의 방명록 글에 대해서만 수정 또는 삭제 폼이 열리길 원한다. 그래야 화면이 복잡해지지 않는다.

### 개발자 정보 및 배포

40. 채점자로서, 페이지에서 개발자 이름 "김동현"과 학번 "202484003"을 바로 확인하고 싶다.
41. 채점자로서, Vercel Production 주소에서 작성·조회·수정·삭제가 모두 실제로 동작하길 원한다.
42. 채점자로서, 비밀번호가 틀린 수정·삭제 요청이 API 수준에서도 거부되는 것을 확인하고 싶다. 그래야 화면을 우회해도 보호된다는 것을 안다.
43. 개발자로서, 한 번의 명령으로 DB 테이블을 만들고 싶다. 여러 번 실행해도 안전해야 한다.
44. 개발자로서, 한 번의 명령으로 로컬 또는 Production 주소를 대상으로 CRUD 전체 흐름을 자동 점검하고 싶다. 그래야 배포 직후 동작을 빠르게 확인할 수 있다.

## Implementation Decisions

### 전체 구조

- Next.js 16 App Router + TypeScript 단일 앱. 페이지는 하나(루트 경로)만 둔다.
- 데이터 변경과 조회는 모두 **Route Handler 기반 REST API**를 거친다. Server Actions는 사용하지 않는다.
- 페이지는 서버에서 첫 목록을 렌더링하고, 작성·수정·삭제는 클라이언트 컴포넌트가 API를 `fetch`로 호출한 뒤 목록을 다시 받아온다. 목록은 항상 최신이어야 하므로 페이지와 API 모두 캐시하지 않는 동적 렌더링으로 둔다.
- DB 접근은 `@neondatabase/serverless`의 HTTP 쿼리 함수로 한다. 연결 문자열은 `DATABASE_URL` 환경변수에서 읽는다. 로컬(`.env.local`)과 Vercel Production이 **같은 Neon DB**를 사용한다.
- Route Handler는 Node.js 런타임으로 실행한다(비밀번호 해시에 Node 내장 `crypto` 사용).
- `package.json`의 `name`을 `guestbook-202484003`으로 바꾼다.

### 모듈

- **Entry 저장소 모듈**: 방명록 글 목록 조회, 작성, 메시지 수정, 삭제를 담당한다. SQL은 이 모듈에만 둔다. 수정·삭제는 id로 저장된 비밀번호 해시를 읽어 비밀번호를 검증한 뒤 수행하고, 결과를 `ok` / `not_found` / `wrong_password` 중 하나로 돌려준다.
- **비밀번호 모듈**: `hashPassword(plain)`과 `verifyPassword(plain, stored)` 두 함수만 노출한다. 구현은 Node 내장 `crypto.scrypt`에 16바이트 랜덤 salt를 쓰고, `salt:hash`(hex) 형식의 문자열로 저장한다. 비교는 `timingSafeEqual`로 한다. 외부 패키지는 추가하지 않는다.
- **입력 검증 모듈**: 작성 입력(이름·메시지·비밀번호)과 수정 입력(메시지·비밀번호)을 trim한 뒤 검증하고, 실패하면 한국어 오류 메시지를 돌려준다. 서버 검증이 최종 기준이다. 클라이언트는 같은 길이 제한을 `maxLength`/`required`로 반영하는 정도로만 사용한다.
- **API Route Handler**: 위 모듈들을 조합해 HTTP 요청과 응답으로 옮긴다.
- **페이지 UI**: 헤더(제목과 개발자 정보), 작성 폼, 방명록 글 목록. 각 글에는 인라인 수정·삭제 폼이 있다.

### DB 스키마

테이블 `entries`:

| 컬럼 | 타입 | 제약 |
|---|---|---|
| `id` | `SERIAL` | PRIMARY KEY |
| `name` | `VARCHAR(20)` | NOT NULL |
| `message` | `VARCHAR(500)` | NOT NULL |
| `password_hash` | `TEXT` | NOT NULL |
| `created_at` | `TIMESTAMPTZ` | NOT NULL, 기본값 `now()` |
| `updated_at` | `TIMESTAMPTZ` | NULL 허용. 메시지 수정 시 `now()`로 설정 |

- 목록 정렬: `created_at DESC, id DESC`(같은 시각일 때 id로 순서 고정).
- 스키마는 SQL 파일로 저장소에 두고, `npm run db:init` 스크립트가 `CREATE TABLE IF NOT EXISTS`로 적용한다(`node --env-file=.env.local`로 실행). 로컬과 Production이 같은 DB이므로 한 번만 실행하면 된다.

### API 계약

공통 규칙:
- 요청과 응답 본문은 JSON이다.
- 오류 응답 형식은 `{ "error": "<한국어 안내 문구>" }`이다.
- 응답에 `password_hash`나 비밀번호를 **절대 포함하지 않는다**.

방명록 글 응답 형식:

```json
{ "id": 1, "name": "김동현", "message": "안녕하세요", "createdAt": "2026-09-30T05:05:00.000Z", "updatedAt": null }
```

| 메서드 · 경로 | 요청 본문 | 성공 | 실패 |
|---|---|---|---|
| `GET /api/entries` | 없음 | `200` 방명록 글 배열(최신순) | `500` |
| `POST /api/entries` | `{ name, message, password }` | `201` 생성된 방명록 글 | `400` 검증 실패 |
| `PATCH /api/entries/[id]` | `{ message, password }` | `200` 수정된 방명록 글 | `400` 검증 실패 / `403` 비밀번호 불일치 / `404` 글 없음 |
| `DELETE /api/entries/[id]` | `{ password }` | `200` `{ "ok": true }` | `400` 비밀번호 누락 / `403` 비밀번호 불일치 / `404` 글 없음 |

- id가 양의 정수가 아니면 `404`로 처리한다.
- `403` 응답 문구는 `"비밀번호가 일치하지 않습니다."`, `404` 응답 문구는 `"이미 삭제되었거나 존재하지 않는 방명록 글입니다."`로 고정한다.
- 예상하지 못한 오류는 `500`과 `"잠시 후 다시 시도해 주세요."`로 응답하고, 자세한 내용은 서버 로그에만 남긴다.

### 입력 검증 규칙

- 모든 문자열은 trim한 뒤 검증한다. 저장도 trim한 값으로 한다. 비밀번호는 trim하지 않고 입력 그대로 해시한다(공백만으로 된 비밀번호는 빈 값으로 거부).
- 이름: 1–20자. 메시지: 1–500자. 비밀번호: 4–20자.
- 문자열이 아닌 값이나 누락된 필드는 빈 값과 같이 `400`으로 처리한다.

### UI 동작

- 헤더에 제목 "방명록"과 "개발자: 김동현 · 학번: 202484003"을 항상 표시한다.
- 작성 폼: 이름, 메시지(textarea), 비밀번호(`type="password"`) 입력란과 [등록] 버튼. 성공하면 폼을 비우고 목록을 갱신한다. 실패하면 폼 아래에 서버가 준 오류 문구를 표시하고 입력은 유지한다. 요청 중에는 버튼을 비활성화한다.
- 목록 항목: 작성자 이름, 작성 시각(`Asia/Seoul`, `YYYY-MM-DD HH:mm`), `updatedAt`에 값이 있으면 "(수정됨)", 메시지(줄바꿈 보존). 그리고 [수정] [삭제] 버튼.
- 인라인 폼은 한 번에 하나만 열린다. 다른 글의 폼을 열면 이전 폼은 닫힌다.
- 수정 폼: 기존 메시지가 채워진 textarea, 비밀번호 입력, [저장] [취소]. 삭제 폼: 비밀번호 입력, [삭제] [취소].
- `403`이면 폼 안에 빨간 글씨로 오류 문구를 표시하고, 입력한 메시지는 유지하며 비밀번호 입력란만 비운다. `404`이면 안내 문구를 표시하고 목록을 갱신한다.
- 스타일은 이미 설치된 Tailwind CSS로 단순하고 깔끔하게 만든다. 가운데 정렬된 좁은 단일 컬럼 레이아웃이다.

## Testing Decisions

- **좋은 테스트의 기준**: 외부에서 관찰 가능한 동작(HTTP 상태 코드, 응답 본문, 목록 순서)만 검증한다. 해시 형식, SQL, 모듈 내부 구조 같은 구현 세부사항은 검증하지 않는다.
- **테스트 경계는 HTTP API 하나뿐이다.** 비밀번호 검증, 입력 검증, 정렬, 해시 비노출이 모두 이 경계에서 드러난다.
- **도구**: 테스트 프레임워크를 추가하지 않는다. Node 내장 `fetch`만 사용하는 smoke 스크립트를 `npm run smoke`로 실행한다. 대상 주소는 `SMOKE_URL` 환경변수로 받고, 기본값은 `http://localhost:3000`이다. Production 확인에는 `SMOKE_URL=https://<production 도메인>`을 넘긴다.
- **smoke 시나리오** (순서대로 실행하고, 하나라도 실패하면 non-zero로 종료):
  1. `POST` 빈 이름 → `400`
  2. `POST` 정상 입력 → `201`, 응답에 `password_hash` 없음
  3. `GET` → 방금 만든 글이 첫 번째, 목록의 어떤 항목에도 `password_hash` 없음
  4. `PATCH` 틀린 비밀번호 → `403`, 메시지 변경 없음
  5. `PATCH` 맞는 비밀번호 → `200`, 메시지 변경됨, `updatedAt` 값 있음
  6. `DELETE` 틀린 비밀번호 → `403`, 글 유지
  7. `DELETE` 맞는 비밀번호 → `200`
  8. `GET` → 해당 글 없음. 같은 id로 `DELETE` → `404`
- smoke 스크립트는 자기가 만든 테스트용 방명록 글을 스스로 삭제한다. 로컬과 Production이 같은 DB를 쓰므로, 도중에 실패하더라도 마지막에 정리 삭제를 시도한다.
- **UI 수동 점검 체크리스트** (로컬과 Production에서 각각 진행):
  - 개발자 이름과 학번이 보이는가
  - 작성하면 맨 위에 나타나고 폼이 비워지는가
  - 틀린 비밀번호로 수정·삭제하면 폼 안에 안내가 뜨고 입력한 메시지가 유지되는가
  - 맞는 비밀번호로 수정하면 "(수정됨)"이 붙는가. 삭제하면 사라지는가
  - 빈 입력은 안내와 함께 거부되는가
- **기존 테스트**: 저장소에 기존 테스트가 없다(Create Next App 초기 상태).

## Out of Scope

- 회원가입, 로그인, 세션, 관리자 기능
- 이름 수정, 작성 시각 수정
- 비밀번호 찾기·변경
- 페이지네이션, 검색, 필터, 무한 스크롤
- 스팸 방지(rate limit, CAPTCHA), 비밀번호 시도 횟수 제한
- 이미지·파일 첨부, 좋아요, 답글
- 실시간 갱신(웹소켓/폴링). 목록은 페이지 로드 시와 자신의 작성·수정·삭제 후에만 갱신된다.
- 자동화된 단위·통합 테스트 프레임워크(Vitest, Jest, Playwright 등)
- 별도의 테스트용 DB나 Neon branch

## Further Notes

- 이 저장소의 Next.js는 16.3.7이다. 구현 전에 `node_modules/next/dist/docs/`에서 Route Handler, 동적 렌더링, 동적 경로 params 관련 가이드를 확인하고 deprecation 안내를 따른다(`AGENTS.md` 지시사항).

- 배포 순서: `npm run db:init`(한 번) → 로컬 `npm run dev` + `npm run smoke` → `npm run build` 확인 → GitHub push → Vercel Production 배포 → `SMOKE_URL=<production>` `npm run smoke` → UI 수동 점검.
- 시험 시간이 제한되어 있으므로 우선순위는 CRUD와 비밀번호 검증이 먼저이고, UI 다듬기는 그다음이다.
